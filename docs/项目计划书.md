# Grey 项目计划书

> 一个轻量、高性能、可扩展的代码 Agent Harness
> 版本：v0.1（草案）｜ 日期：2026-08-16 ｜ 状态：规划中

---

## 1. 背景与痛点

现有 code agent / Harness 工具存在两类典型问题：

| 痛点 | 表现 |
| --- | --- |
| **臃肿** | 安装体积大、启动慢、依赖重；为少数用户场景塞入大量功能，日常 80% 的路径只用到 20% 的功能 |
| **不够强** | 上下文管理粗糙导致 Token 浪费；单 Agent 单线程、缺乏编排；对编程场景（LSP、文档、读图）支持不足 |
| **不够顺手** | 界面布局固定不可定制；完成提醒弱；难以接入用户已有的 MCP / Hook / 工作流 |

**Grey 的定位**：不是另一个"全家桶 IDE"，而是一个**内核轻、能力可插拔、界面可定制**的 Agent 运行环境（Harness）。核心信条：

> 默认极简，一切按需扩展。快是特性，省是特性，顺是特性。

---

## 2. 愿景与核心原则

### 2.1 一句话愿景

> 让用户"自己的 AI 工作流"以最低成本跑起来：少花 Token、少等启动、少被界面绑架。

### 2.2 核心原则（贯穿所有阶段的决策标准）

1. **轻量优先**：单二进制 / 无运行时依赖；启动时间 < 300ms 目标；所有重功能走插件或按需加载。
2. **省 Token 是内置能力**：不是事后优化，而是上下文管理、压缩、缓存从第一天就是一等公民。
3. **可扩展是架构，不是口号**：Provider、Agent、工具、UI 布局、Hook、MCP 全部走统一接口。
4. **编程场景特化**：LSP 语义感知、文档检索、图像理解为内建能力，而不是"能用"的水平。
5. **界面可定制但开箱即美**：默认布局好看好用，同时像 lazyvim 一样支持配置化布局。
6. **一切可配置，默认有最优解**：配置文件驱动，但默认值就是推荐值。

## 4. 技术选型

### 4.1 候选方案对比

| 维度 | **Rust + ratatui**（推荐） | Go + bubbletea | TypeScript + Ink |
| --- | --- | --- | --- |
| 性能 / 内存 | ★★★★★ 零 GC，单二进制 | ★★★★ GC 可控 | ★★★ Node 底座重 |
| 启动速度 | ★★★★★ | ★★★★★ | ★★ |
| TUI 生态 | ratatui 成熟（lazygit 同源） | bubbletea 活跃 | Ink 较新 |
| LSP 生态 | tower-lsp（rust-analyzer 同源） | go-lsp / glsp 较薄 | vscode-languageserver 成熟 |
| 插件系统 | 动态库难，倾向 WASM / 脚本桥接 | 同左 | 天然 JS 生态 |
| 开发效率 | ★★ 需耐心 | ★★★ | ★★★★★ |
| 团队成本 | 需 Rust 功底 | 易上手 | 最低 |

### 4.2 推荐方案

**主选：Rust + ratatui + tower-lsp**

理由：
- "轻量且性能优秀"（需求 7）是 Rust 的主场；单二进制分发，零依赖安装。
- ratatui 是 lazygit 同款 TUI 框架，"美观可定制布局"（需求 9）有现成范式。
- tower-lsp 与 rust-analyzer 同源，LSP 集成（需求 4）质量有保障。
- 插件与扩展（需求 8）采用 **WASM 插件 + 内置 Lua/TOML 配置** 双轨制（参考 Helix / Neovim 思路）。

**备选：若团队无 Rust 经验且求快，可降级为 Go + bubbletea**（架构设计保持语言无关，接口先行）。

> ⚠️ **Phase 0 决策门**：在正式动手前，用 3 天做一个"技术侦察 Spikes"（见阶段文档），验证 TUI 渲染性能、LSP 接入、流式渲染三条核心链路，再锁定语言。

### 4.3 关键依赖候选（Rust 方案）

| 领域 | 候选库 |
| --- | --- |
| TUI | ratatui + crossterm |
| LSP | tower-lsp |
| 异步 | tokio |
| 序列化 | serde / serde_json |
| HTTP/SSE | reqwest + eventsource-stream |
| 终端图像 | viuer / kitty / sixel 协议 |
| 桌面通知 | notify-rust |
| 配置 | toml / serde（+ 可选 Lua: mlua） |
| 搜索 | ripgrep（rg 库） |
| SQLite | rusqlite（缓存/历史） |

## 5. 系统架构（目标态）

```
┌────────────────────────────────────────────────────────────┐
│                        UI 层 (TUI)                          │
│  布局系统(类lazyvim) │ 主题系统 │ 快捷键 │ 输入/流式渲染     │
└───────────────┬────────────────────────────────────────────┘
                │ 事件总线 (Event Bus)
┌───────────────▼────────────────────────────────────────────┐
│                    核心运行时 (Core)                        │
│  ┌───────────┐ ┌───────────┐ ┌──────────────────────────┐  │
│  │ Agent 编排 │ │ 会话/状态  │ │ 上下文管理(Context Mgr)  │  │
│  │ (Orchestra)│ │ (Session) │ │ 压缩/裁剪/缓存/摘要      │  │
│  └───────────┘ └───────────┘ └──────────────────────────┘  │
│  ┌───────────┐ ┌───────────┐ ┌──────────────────────────┐  │
│  │ 工具系统   │ │ 模型路由   │ │ Hook 引擎                │  │
│  │ (Tools/MCP)│ │ (Router)  │ │ 生命周期钩子/权限         │  │
│  └───────────┘ └───────────┘ └──────────────────────────┘  │
└───────────────┬────────────────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────────────────┐
│                  集成层 (Integrations)                      │
│  Provider 适配器(OpenAI/Anthropic/Gemini/Ollama/...)       │
│  LSP 客户端(tower-lsp) │ 代码检索(rg) │ 文件系统 │ 图像     │
└────────────────────────────────────────────────────────────┘
```

### 5.1 分层原则

- **UI 与 Core 解耦**：通过事件总线通信，未来可换 Web UI / 桌面 GUI 而不动内核。
- **Provider 是一等抽象**：所有模型差异（工具调用格式、流式、图像输入、推理）收敛到 `Provider` trait。
- **上下文管理是独立模块**：任何 Agent 的对话都必须经过 Context Manager，杜绝绕过。
- **工具即 MCP**：内建工具与 MCP 工具统一为同一接口，`MCP Client` 只是工具的一种来源。

## 6. 竞品与差异化

| 产品 | 可借鉴 | Grey 的差异点 |
| --- | --- | --- |
| Claude Code / Crush | 工具调用循环、Hook、会话体验 | 更轻、布局可定制、多 Agent 编排更显性 |
| Aider | repo map、diff 注入省 Token | 引入 repo map 思路并增强（结合 LSP） |
| OpenHands | Agent 编排、事件流 | 本地化、轻量、TUI 而非 Web 全家桶 |
| lazygit / lazyvim | 布局、快捷键、主题哲学 | UI 哲学直接对标 |
| Cursor / IDE 助手 | LSP 深度集成 | 不做 IDE，做"Harness" |

**Grey 的护城河**：不是某一项功能，而是 **轻量 × 省 Token × 可定制** 的组合体验，以及"为编程场景深度优化"的专注度。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Rust 开发速度慢 | 整体延期 | Phase 0 Spikes 先行；先薄后厚；必要时降级 Go |
| TUI 流式渲染性能 | 体验差 | 增量渲染 + 双缓冲基准测试写进 CI |
| Provider 格式差异爆炸 | 维护负担 | 只做 OpenAI 兼容 + 少而精的原生适配；差异收敛到适配层 |
| 省 Token 策略引入 bug | 对话质量下降 | 上下文压缩全部可回滚 / 可审计，默认保守 |
| 多 Agent 并行上下文混乱 | 结果错乱 | 严格上下文隔离 + 显式共享机制 |
| 桌面形象与提醒过度打扰 | 用户反感 | 默认弱提醒，强提醒可配置 |
