# Grey 阶段性开发文档

> 从零到 v1.0 的开发路线图：每个阶段包含目标、交付物、关键技术点、验收标准。
> 配套阅读：《项目计划书》。本文档随开发持续更新。

---

## 阶段总览

| 阶段 | 名称 | 目标 | 周期 |
| --- | --- | --- | --- |
| P0 | 侦察与脚手架 | 技术验证，锁定选型 | 1–2 周 |
| P1 | 最小可用对话 | 问→答→改代码闭环 | 3–4 周 |
| P2 | 多 Provider 与省 Token | 核心体验稳定、成本可控 | 3–4 周 |
| P3 | Agent 编排与 MCP | 多 Agent 与工具生态 | 3–4 周 |
| P4 | LSP 与编程特化 | 编程场景质变 | 3–4 周 |
| P5 | UI 定制与完成提醒 | 颜值与体验 | 2–3 周 |
| P6 | 扩展系统与性能打磨 | 插件、基准达标 | 3–4 周 |
| P7 | 发布 v1.0 | 文档、打包、公开 | 2 周 |

每个阶段的通用守则：

1. **先跑通再打磨**：每阶段先实现纵向切片，再横向补全。
2. **测试随行**：核心逻辑必须有单元测试；性能基准进入 CI。
3. **文档随行**：每个阶段交付用户文档 + 架构决策记录（ADR）。
4. **每阶段结束有演示**：验收 = 演示 + 测试通过 + 文档齐。

## P0 侦察与脚手架（1–2 周）

### 目标
用最小代码验证三条核心链路，回答"选 Rust 还是 Go"的决策门问题。

### 交付物
- [ ] 3 个 Spike 原型（每个 ≤ 300 行）：
  - **Spike A**：TUI 流式渲染 — 一边收 SSE 流一边增量渲染，验证帧率与内存（目标渲染延迟 < 16ms/帧）
  - **Spike B**：LSP 接入 — 连接 rust-analyzer，获取诊断与定义跳转
  - **Spike C**：Provider 对话 — OpenAI 兼容 + Anthropic 双适配，含流式与工具调用格式差异
- [ ] 仓库骨架：`cargo workspace` 或 Go module，目录结构、CI（fmt + lint + test）、`.gitignore`
- [ ] 配置系统初版：TOML 配置文件 + 环境变量 + CLI 参数三态合并
- [ ] 决策记录 ADR-001：锁定语言与 TUI/LSP 框架

### 关键技术点
- ratatui 增量渲染：只重绘脏区域；双缓冲
- tokio 流式管道：`stream → channel → UI` 背压处理
- Provider trait 首版接口草案（为 P2 打底）

### 验收标准
- Spike 三件套可演示
- 决策门通过，架构文档 v1 定稿
- 新成员 clone 后一条命令跑起 demo

## P1 最小可用对话（3–4 周）

### 目标
**纵向切片**：一个 Provider、一个工具、一个简单 TUI，跑通"我问→它答→它改代码→我确认"的完整闭环。

### 交付物
- [ ] CLI 入口：`grey` 启动 TUI；支持 `grey "prompt"` 单发模式
- [ ] 对话循环：流式输出、中断（Ctrl-C）、错误恢复、重试
- [ ] 工具系统 v1：`read_file` / `edit_file` / `bash` / `glob` / `grep`（文件操作一律走事务式安全编辑：先读→精确替换→测试）
- [ ] 会话持久化：历史会话保存/恢复（SQLite）
- [ ] 极简 TUI：输入框 + 输出区 + 状态栏；默认配色主题
- [ ] 系统提示词工程 v1：任务描述、工具使用规范、"只改该改的"

### 关键技术点
- 工具调用的结构化循环（assistant → tool_call → tool_result → assistant）
- 编辑安全：`old_string` 精确匹配、替换后自检、失败回滚提示
- 流式输出在 TUI 中的增量渲染

### 验收标准
- 能在一个小仓库里完成"找 bug → 修复 → 跑测试验证"的完整任务
- 中断/重试/断网等异常路径不崩溃
- 单发模式可脚本化（供未来 Agent 编排复用）

## P2 多 Provider 与省 Token（3–4 周）

### 目标
接入多家模型，并把"省 Token"变成默认能力。

### 交付物
- [ ] Provider 适配器：OpenAI 兼容协议（覆盖 DeepSeek、Ollama、vLLM 等）+ Anthropic + Gemini
- [ ] 模型路由：按任务选模型（如"规划用强模型、编辑用快模型"）；手动 / 自动切换
- [ ] 故障切换：请求失败自动降级到备用 Provider
- [ ] 上下文管理器（Context Manager）：
  - 系统提示精简与按需注入
  - 对话裁剪策略（保留最近 N 条 + 关键上下文锚点）
  - 历史摘要（滚动摘要）
  - 工具输出截断 / 摘要注入（大文件只注入 diff 与关键行）
- [ ] 请求缓存：相同前缀请求缓存（本地 SQLite），显著降成本
- [ ] 用量统计面板：每会话 Token 消耗、成本估算

### 关键技术点
- 上下文预算模型：Token 计数（tiktoken 兼容算法）→ 预算分配（系统/历史/工具输出/新输入）
- 摘要策略：异步生成摘要，主对话不被阻塞
- 缓存 key 设计：模型 + 前 N 个消息 hash

### 验收标准
- 同一对话可在多个 Provider 间无缝切换
- 长对话（100+ 轮）Token 消耗比无管理下降 ≥ 40%
- 所有压缩策略可开关、可审计（日志记录压缩了什么）

## P3 Agent 编排与 MCP（3–4 周）

### 目标
从"单 Agent"升级为"可编排的多 Agent 系统"，并接入 MCP 生态。

### 交付物
- [ ] Agent 抽象：`Agent` trait（prompt、tools、model、context 可配置）
- [ ] 子 Agent 派生：主 Agent 可 spawn 研究员 / 编码器 / 审阅者等子 Agent，共享会话但上下文隔离
- [ ] 并行编排：多个子 Agent 并行跑，结果汇总回主 Agent
- [ ] 任务委派协议：主 Agent 如何描述任务、子 Agent 如何回报（结构化结果）
- [ ] MCP Client：连接 MCP 服务器，把 MCP 工具注册进工具系统（工具即 MCP 的统一接口落地）
- [ ] 常用 MCP 适配：filesystem、github 等参考实现

### 关键技术点
- 上下文隔离与显式共享：子 Agent 只看到被授权的上下文
- 结果合并策略：结构化回报（成功/失败/产出文件列表/diff）
- MCP 协议：stdio + SSE 传输；工具 schema 转换

### 验收标准
- 一个"大任务"（如实现一个功能模块）可委派给 3 个子 Agent 并行完成
- MCP 服务器可即插即用，内建工具与 MCP 工具统一管理
- 子 Agent 上下文互不污染（并发测试）

## P4 LSP 与编程特化（3–4 周）

### 目标
让 Grey 拥有 IDE 级的代码理解能力，并把文档/读图能力做深。

### 交付物
- [ ] LSP 客户端（tower-lsp）：
  - 诊断实时流入会话（Agent 可感知编译错误）
  - 定义 / 引用 / 符号 / 悬停 / 重命名 → 暴露为 Agent 工具
- [ ] "语义视图"：把 LSP 结果转成紧凑的上下文注入（如"修改 `foo` 会影响 3 个调用点"而非贴全文）
- [ ] 代码检索增强：ripgrep + 符号索引；可选的 repo map（Aider 思路 + LSP 增强）
- [ ] 文档特化：README/文档片段检索注入；支持常见文档格式提取
- [ ] 读图能力：
  - 终端内图片渲染（kitty / sixel / iTerm 协议，回退为 ASCII 预览）
  - 图像作为多模态输入传给支持视觉的模型（截图、图表、UI mock 评审）
  - 本地小模型 OCR 提取（可选）

### 关键技术点
- LSP 多语言配置（按项目推断 language server，可自定义）
- 语义视图的 Token 预算：把 LSP 输出压缩到"最少必要信息"
- 图像协议协商：终端能力探测 → 降级链

### 验收标准
- 对话中可直接"跳到定义、查引用、看诊断"，Agent 回答基于真实语义而非纯文本猜测
- 给一张截图/报错图，模型能基于图片内容回答
- 语义视图注入使 Token 消耗低于贴原文

## P5 UI 定制与完成提醒（2–3 周）

### 目标
体验与颜值的质变：类 lazyvim 的布局系统 + 强完成提醒 + 桌面形象。

### 交付物
- [ ] 布局系统：配置化分栏（输入 / 对话 / 文件树 / 诊断面板 / 子 Agent 面板），支持拆分、折叠、拖动（如可行）
- [ ] 状态栏：模型、Token 用量、当前任务、分支、错误徽标
- [ ] 快捷键体系：默认键位表（vim 风格优先），可配置、可查（`<leader>k`）
- [ ] 主题系统：配色主题（内置若干 + 自定义），可随终端明暗切换
- [ ] 动画与反馈：流式输出光标、任务切换动效（克制原则，不炫技）
- [ ] 完成提醒：
  - 桌面通知（notify-rust）：任务完成/失败/需确认
  - 可选声音 / 终端铃
  - **强完成提醒**：长任务（> 阈值）完成时置顶提醒、可配置"完成后鸣铃直到我回来"
- [ ] 桌面形象 v1：托盘/常驻角标显示运行状态（空闲/工作中/完成），点击可打开会话摘要

### 关键技术点
- 布局树抽象（Layout Tree）：与 UI 逻辑解耦，纯配置驱动
- 通知分级：轻（静默）/ 中（角标）/ 强（置顶+声音），用户可配
- 托盘与通知跨平台抽象（macOS / Linux / Windows）

### 验收标准
- 默认布局开箱即美；布局/主题/键位三件套均可配置且热重载
- 长时间任务完成后，即使终端在后台也能被可靠提醒
- 桌面形象不干扰日常使用（默认轻打扰）

## P6 扩展系统与性能打磨（3–4 周）

### 目标
兑现"可扩展性强"承诺：插件系统 + 性能达标。

### 交付物
- [ ] 插件系统 v1（WASM 插件 + 配置扩展双轨）：
  - 插件可注册：新工具、新 Provider 适配、新 UI 面板、新 Hook
  - 插件清单 / 版本 / 沙箱（WASM 隔离）
  - 示例插件：自定义工具、自定义主题
- [ ] Hook 引擎（补齐生命周期）：
  - 事件：会话开始/结束、工具调用前/后、消息发送前、权限决策、完成提醒
  - Hook 可阻断/改写/注入上下文
- [ ] Loop / Goal 支持：
  - Loop：任务循环（重试直到通过、批量处理）
  - Goal：目标定义 → 计划 → 执行 → 自我校验 → 完成判定
- [ ] 性能基准 CI：
  - 启动时间 < 300ms；内存基线；长对话渲染帧率；大仓库（10 万文件）操作延迟
- [ ] 性能优化：懒加载（LSP 按需启动）、增量索引、并行化、内存剖析

### 关键技术点
- WASM 插件 ABI 设计（与 Core 类型系统映射）
- Hook 的同步/异步、可阻塞语义；防死锁
- Goal 的完成判定：测试通过 / 用户确认 / 自检打分

### 验收标准
- 第三方插件可独立发布、安装、卸载，不重启 Core
- Hook 可覆盖 80% 的常用生命周期场景
- 性能基准全绿（CI 门禁）

## 附录 A：建议仓库结构（Rust 方案）

```
grey/
├── Cargo.toml               # workspace
├── crates/
│   ├── grey-core/           # 核心运行时：会话、上下文、编排
│   ├── grey-provider/       # Provider 抽象与适配器
│   ├── grey-tools/          # 内建工具集
│   ├── grey-lsp/            # LSP 客户端与语义视图
│   ├── grey-mcp/            # MCP 客户端
│   ├── grey-tui/            # 布局、主题、渲染
│   ├── grey-hooks/          # Hook 引擎
│   └── grey-cli/            # 入口、配置、命令
├── docs/
│   ├── 项目计划书.md
│   ├── 阶段性开发文档.md
│   └── adr/                 # 架构决策记录
├── tests/                   # 集成测试 / 性能基准
└── plugins/examples/        # 示例插件
```
